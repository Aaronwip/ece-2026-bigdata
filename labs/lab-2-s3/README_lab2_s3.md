## Environment

The `default` AWS profile is created from the init script of the Onyxia "S3 Profile Detail" page
(`AWS CLI / shared profile`). Without it, `aws configure list --profile 'default'` fails with
`The config profile (default) could not be found`, while commands without `--profile` still work thanks to the
`AWS_*` environment variables.

```bash
export S3_ENDPOINT_URL=$(aws configure get endpoint_url --profile 'default' || echo "https://$AWS_S3_ENDPOINT")
export LAB_BUCKET_NAME="$KUBERNETES_NAMESPACE"
export AWS_PAGER=""   # avoid the interactive pager on long outputs
```

## Upload, list, download

```bash
uv run dataset-users -o csv > users.csv
aws s3 --profile 'default' cp users.csv "s3://$LAB_BUCKET_NAME/bronze/users.csv"
aws s3 --profile 'default' ls "s3://$LAB_BUCKET_NAME/bronze/"
#> 2026-10-11 20:34:03       7351 users.csv
```

`users.csv` has 101 physical lines for 50 users: the addresses generated by Faker span two lines and are quoted in
the CSV. The size, 7351 bytes, matches the lab because the generator uses a fixed seed.

Pitfall: when `dataset-users` fails (project not installed, `uv sync` missing), the redirection `>` still creates an
empty `users.csv`, which is then uploaded. Always check the file before uploading.

## Metadata

```bash
aws s3api --profile 'default' head-object --bucket "$LAB_BUCKET_NAME" --key bronze/users.csv
#>   "ContentLength": 7351,
#>   "ETag": "\"38e52148a53c2315573ce62bc7ce3330\"",
#>   "ContentType": "text/csv",
#>   "Metadata": {}
md5sum users.csv
#> 38e52148a53c2315573ce62bc7ce3330  users.csv
```

The ETag equals the MD5 of the file: the object was uploaded in a single `PUT`.

## Versioning

Three uploads of `bronze/users.csv`, then a delete:

| VersionId | Size | Meaning |
| --- | --- | --- |
| `null` | 7351 | uploaded **before** versioning was enabled, kept with the `null` ID |
| `67226baecb5346f5d8866e2f1a245071` | 7351 | version 1, 50 users |
| `67226bae4a83c4ba938c8c812464e6af` | 5855 | version 2, 40 users |
| `67226b7f23825f910da5ce4a85a94454` | — | delete marker, `IsLatest: true` |

Version 1 is restored with `get-object --version-id 67226baecb5346f5d8866e2f1a245071` and is identical to the
local `users.csv`. The `rm` did not remove any data: it only added a delete marker, all versions stay recoverable.

## Upload the datasets from a Kubernetes Job

The first run of [`job-upload-bronze.yaml`](./job-upload-bronze.yaml) never completed: `kubectl wait` timed out and no
pod was created. The cause was found in the events of the Job:

```bash
kubectl describe job upload-bronze
#> Warning  FailedCreate  job-controller  Error creating: pods "upload-bronze-8nwvv" is forbidden:
#>   failed quota: onyxia-quota: must specify limits.cpu for: upload
```

The namespace has a `ResourceQuota` which requires a CPU limit on every container. The fix adds `cpu: 500m` under
`limits`:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi
```

After the fix, the Job completes and uploads `bronze/users.csv` and `bronze/orders.csv`. The Kubernetes objects are
then deleted, the bronze objects are kept for the next modules.

### Questions

**Why are the credentials stored in a Secret and not in the ConfigMap?**
A ConfigMap is meant for non-sensitive configuration: it is readable by anyone with read access to the namespace and is
displayed in clear text by `kubectl describe`. A Secret is a dedicated object for sensitive data: access can be
restricted separately with RBAC, it is not displayed by `kubectl describe`, and it can be encrypted at rest. It also
separates the configuration (endpoint, bucket) from the credentials, which have a different lifecycle.

**The credentials of Onyxia are temporary. What happens if the Job is executed again tomorrow? How would a production
platform provide credentials to a Job?**
The session token stored in the Secret will have expired: the `aws s3 cp` fails with `ExpiredToken` or
`AccessDenied`, the Job retries up to `backoffLimit` and ends in failure. In production, credentials are not copied
by hand: the Job uses a Kubernetes ServiceAccount bound to an IAM role (IRSA on AWS, Workload Identity on GCP/Azure),
which obtains short-lived credentials automatically, or a secret manager (Vault, External Secrets Operator) renews the
Secret.

**How would you turn this Job into a daily ingestion?**
By wrapping the Job template in a `CronJob` with a schedule such as `schedule: "0 2 * * *"` (every day at 2:00).
The data would be read from the source system instead of a ConfigMap, and written under a partitioned key such as
`bronze/users/date=2026-10-11/users.csv` so that each run does not overwrite the previous one. An orchestrator
(Airflow, Argo Workflows) is an alternative when the ingestion has dependencies.
